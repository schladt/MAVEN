## MAVEN memory integration

At startup (or the first eligible main-agent turn when native hooks are unavailable), visibly say `MAVEN: checking…`. Call `maven_status` with workspace `cwd` and, when actually supplied by the harness hook, its genuine `harness` and `harness_session`. Then use `maven_startup` with the same identity and `action="inspect"`. A hook's local output is routing context, not cloud readiness or capture consent. Inside an explicitly enabled project, use the returned selection; a Git repository alone is not enablement. Otherwise ask the returned `start_hint.question` every time: **Start Home** → `maven_startup(home=true, action="continue", ...)`; **Create Project** → `maven_project` with explicit root/scope and an existing cloud project or authorized creation; **Read Only** → `maven_start(choice="read_only", ...)`. No answer means Read Only. Read Only creates no session and captures nothing; consult unbound universal/Home only when asked. Subagents inherit their originating binding and never run startup.

Always print the returned `active.line` (for example `MAVEN: Home (<label>)`, `MAVEN: project <label>`, `MAVEN: read-only`) at start and whenever it changes.

For an unambiguous enabled project, visibly say `MAVEN: initializing for <project>...` and call `maven_startup(action="continue", ...)`. It resumes only this exact native conversation's retained binding, preserving pause; a new conversation starts a distinct session. A completed session is not reopened. If stale/unfinished peers require a choice, offer review recovery, explicitly start new with `action="new"` leaving peers untouched, or Read Only. Age never proves a writer stopped. When no genuine native conversation identity is exposed, retain explicit binding from this conversation and use `maven_initialize` to restore it; never choose a peer by cwd, PID, name, or recency. Keep root/project/session/instance and operation references; cwd changes never rebind them.

After harness/MCP restart, inspect status before saying connected. A `rebind_hint` is not permission to take over a listed peer: resume only its exact `binding` matching this native conversation, or the exact binding retained in this conversation. New conversations use new sessions and previous handovers. Use `maven_diagnose` for read-only local repair choices and `maven_startup(action="inspect")` for cloud session status. Recovery must preserve original requests and requires actual relevant-worker quiescence. Outside a selected project or Home, consultation stays read-only and only on owner request.

Scope: universal holds preferences, instructions and general lessons only, never anything specific to one customer or project, because universal records appear in every project. Home holds the owner's life, personal and work tasks, and awareness of people and organizations (for example tag `client:<slug>`). Project detail stays in its project. When unsure, choose Home, not universal. Home is a per-machine opt-in set up, changed or disabled through `maven_admin` kind `home` or the installer entry "Set up or change MAVEN Home".

Read all returned current universal/project authority, exact dependencies, handover, tasks, blockers, peers and pending operations; follow pagination/artifact ranges without truncating authority. Only then print the returned ready `message` and `active.line`. Preserve a restored pause. Reload with `maven_context` after compaction. Tool discovery, a hook firing or an MCP connection is not readiness; report blocked/degraded authority honestly. `project_index.is_current_context` identifies the project whose context is being viewed, not all machines' Home selections or retained Home tags. Native adapters are optional; this guidance remains the first-turn fallback when they are unavailable.

When peers are stale or an earlier end event lacks verified closure, report the machine, available activity/evidence, and offer recovery or leaving it open. Never auto-close or take over. Owner-confirmed peer closure uses `maven_close_peer` with its exact revision; age is not confirmation. For a requested wrap-up-and-exit, pause new automatic maintenance, finish accepted work, checkpoint, and call `maven_finish`; only a verified close permits automatic exit. On failure stay open and explain pending work/paused mode. OMP's optional exit guard can ask before shutdown; other shutdown hooks are best-effort evidence only. Crashes/forced exits are recovered on the next startup, never reported as successful wrap-up.

To switch an already-bound folder to an existing cloud project, use the explicit `switch` mode in `maven_admin` project/Home administration. Present exact old/new IDs, instance, folder, preservation path and session blockers; wait for owner approval. Old cloud records and other machines remain unchanged. Do not rename/delete the folder, edit its binding manually, merge cloud projects, or archive old data as an implicit repair.

Use the `maven` skill as the single conversational front door: save, consult, status, reconcile, checkpoint, checkpoint and wait, pause, resume, resume fresh, wrap up, setup, diagnosis/removal, and explicitly requested Git assistance. Resolve IDs/revisions and tool schemas yourself; owners should not compose commands or JSON. Automatically maintain meaningful authorized decisions, tasks, plans, blockers, and verified outcomes, not whole transcripts, credentials, or indiscriminate source uploads.

Use the `maven-maintenance` role for bounded semantic reconciliation. Register the assignment through `maven_maintenance`, hand the actual source evidence and originating binding to a harness-native background subagent when that runtime supports MCP access and result delivery, then continue unrelated conversation. OMP's task workers and current Claude Code background subagents support this; use the native tool actually advertised in the session, never invented hook syntax. Other clients may expose equivalent native agents; only use them after confirming those capabilities. Otherwise perform the same role in the foreground and disclose the fallback. A pending tool result is not a spawned model or proof of responsiveness. Never start an independent daemon or model runtime.

Keep routine successes quiet. Confirm explicit saves only with verified cloud receipts. Show checkpoint preparation/completion, pause/resume mode, failures, conflicts, uncertainty, and unavailable memory. Summarize universal updates/promotions, project updates, and pending work only on request, checkpoint completion, or explicit wrap-up. AWS is durable authority; private local pending evidence is not cloud-saved. Continue unrelated work during outages, but do not proceed using unavailable/stale governing authority. Do not log in, change identity, deploy, activate instructions, or publish Git implicitly.
