## MAVEN memory integration

At the first user turn of each main work session, before governed work, call `maven_status` with the workspace directory as `cwd`. Installation/tool discovery alone is not capture consent. Inside an enabled project (`.maven/project.json` at or above `cwd`), initialize it as below. Otherwise, if the result carries a `start_hint`, ask its one-line `question` every time, even when a `last_choice` is shown, and act on the answer: **Start Home** → `maven_initialize` with `home=true` and `cwd`; **Create Project** → normal enablement with explicit project/root/scope consent through `maven_project` (it refuses `$HOME`, `/`, `~/.maven` and the MAVEN checkout); **Read Only** → `maven_start` with `choice="read_only"` and `cwd`. No answer means Read Only. The answer is recorded locally only. Read Only creates no session and captures nothing; consult only when the owner asks, with `unbound=true` and optionally `include_home=true`. Never capture without a project or Home choice. No Git repository or no-Git choice is required. Never silently ascend to a repository root or choose a root yourself; the owner-configured Home is the one explicit exception. Never rebind when `cwd` changes. Subagents and maintenance workers inherit the parent's choice and never ask.

Always print the returned `active.line` (for example `MAVEN: Home (<label>)`, `MAVEN: project <label>`, `MAVEN: read-only`) at start and whenever it changes.

For an enabled project, visibly say `MAVEN: initializing for <project>...`, then use the discovered `maven_initialize` tool with the exact absolute root and actual harness name. A new chat/fork gets a new MAVEN session; an explicitly resumed chat uses its exact retained binding. Retain home/instance/root/project/session and operation references in the harness's session context. Never infer an identity from cwd changes, a process ID, newest receipt, or another conversation. A worker with an originating assignment must not run fresh startup or create a replacement session.

After a harness or MCP restart, call `maven_status` (with `cwd`) before saying MAVEN is connected or ready. A new MCP process is unbound: if it reports `not_initialized` with a `rebind_hint`, resume only the exact retained session (`maven_initialize` with that `session_id` and `resume=true`), never the newest listed one. Outside a project or Home session, consultation stays read-only (`maven_search`/`maven_read` with `unbound=true`, plus `include_home=true` when Home is wanted) and only when the owner asks; it creates no session and captures nothing.

Scope: universal holds preferences, instructions and general lessons only, never anything specific to one customer or project, because universal records appear in every project. Home holds the owner's life, personal and work tasks, and awareness of people and organizations (for example tag `client:<slug>`). Project detail stays in its project. When unsure, choose Home, not universal. Home is a per-machine opt-in set up, changed or disabled through `maven_admin` kind `home` or the installer entry "Set up or change MAVEN Home".

Read the entire returned current context: all applicable universal/project governing instructions and exact dependencies, handover, tasks, blockers, peers, and pending operations. Follow pagination/artifact ranges without truncating authority. Use `maven_context` to refresh after restoration/compaction; retain routing references, not cached authority. Only after verified binding and complete current context say the returned ready `message` (`MAVEN: ready — project context loaded; automatic memory updates enabled.`, or `MAVEN: ready — Home (<label>) context loaded; automatic memory updates enabled.` for Home). Respect a restored pause and say `MAVEN: ready — automatic memory updates paused.` Otherwise say `MAVEN: initialization blocked — <reason>.` MCP connection status or stderr is never readiness. If startup context is disabled, shadowed, or truncated, automatic initialization is unavailable; disclose it and explicitly load the MAVEN skill before governed work. This is first-turn agent guidance, not an executable startup hook.

When `active_peers` lists a peer with `stale: true`, tell the owner its `machine` and `last_activity` and offer to close it; call `maven_close_peer` with its `session_id` and `revision` only after the owner explicitly says yes.

Use the `maven` skill as the single conversational front door: save, consult, status, reconcile, checkpoint, checkpoint and wait, pause, resume, resume fresh, wrap up, setup, diagnosis/removal, and explicitly requested Git assistance. Resolve IDs/revisions and tool schemas yourself; owners should not compose commands or JSON. Automatically maintain meaningful authorized decisions, tasks, plans, blockers, and verified outcomes, not whole transcripts, credentials, or indiscriminate source uploads.

Use the `maven-maintenance` role for bounded semantic reconciliation. Register the assignment through `maven_maintenance`, hand the actual source evidence and originating binding to a harness-native background subagent when that runtime supports MCP access and result delivery, then continue unrelated conversation. OMP's task workers and current Claude Code background subagents support this; use the native tool actually advertised in the session, never invented hook syntax. Other clients may expose equivalent native agents; only use them after confirming those capabilities. Otherwise perform the same role in the foreground and disclose the fallback. A pending tool result is not a spawned model or proof of responsiveness. Never start an independent daemon or model runtime.

Keep routine successes quiet. Confirm explicit saves only with verified cloud receipts. Show checkpoint preparation/completion, pause/resume mode, failures, conflicts, uncertainty, and unavailable memory. Summarize universal updates/promotions, project updates, and pending work only on request, checkpoint completion, or explicit wrap-up. AWS is durable authority; private local pending evidence is not cloud-saved. Continue unrelated work during outages, but do not proceed using unavailable/stale governing authority. Do not log in, change identity, deploy, activate instructions, or publish Git implicitly.
