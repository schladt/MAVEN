# Explicit owner-reviewed installation and setup

Proposed skill: use only as current applicable owner-approved authority. Installation, service/schema deployment and instruction activation are separate decisions; local code/template updates never authorize live changes.

## Installation and connection

Use the reviewed installer for first-time local installation. It creates isolated code, private configuration and recovery commands; no preexisting environment or project `.maven` is needed. Explain the selected home, package downloads and harness destinations. Core agentic installation includes MCP; Google is optional. A standard client launches the stdio process without a persistent server or model service. Installation alone is not readiness or permission to capture conversations.

Through conversation, present the shared resumable controller's full persisted interactions. Bind responses to exact operation/interaction identity, revision, choices and review digest; record genuine harness-origin consent, never a fabricated TUI click. Use CLI/TUI for recovery and unavoidable protected handoffs. Login/browser consent and secret input require explicit secure handoff; do not request credentials in chat.

Stage harness configuration/guidance changes for review, preserving unrelated entries and conflicts. A running harness cannot attest that it has stopped. Require external continuation with affected harnesses closed before applying protected integration changes. Track exact ownership for removal; custom profiles/destinations must be explicit.

Connect an existing instance by reviewed settings import or actual selected-stack outputs. Neither deploys, reinitializes the database nor replaces active authority. Validate runtime identity separately from administration. Do not inherit another machine's credential-cache paths or fall back to root/default profiles. Resume interrupted setup with its original private reviews, request identities and uncertain receipts, not a replacement installation.

## Provisioning and upgrades

Before provisioning, establish explicit account, region, profiles, least-privilege roles, resource names, network constraints and budget. Review exact generated infrastructure, package/policy digests, capabilities, parameters, role trust, resource changes and continuing costs. Change-set creation, exact execution, database initialization/migration and each instruction activation require separate owner-reviewed actions. Do not broaden permissions or network access to pass a check. Use real confirmed outputs, never example identities.

Existing-instance memory-contract cutover requires matching service/schema rollout before ordinary use. Preserve historical Git checkpoints and pending publication/setup/removal receipts; recover incompatible operations with their original supported implementation first. New memory checkpoints are not reconstructed from old publication receipts. Detect incompatibility rather than bypass validation. Reconnect using reviewed upgraded outputs without silently editing installed user configuration.

Prepare authority proposals locally and review each complete body/dependency. Submit only approved candidates, obtain real activation challenges and exact owner approval evidence, activate dependencies first, then reread current active authority. Never bulk-activate the catalog or treat schema approval as policy approval. Report local installation, instance readiness, project readiness and live rollout separately.

## Project enablement and removal

Project setup is optional during instance onboarding. Confirm an absolute folder independently of installation, reject `/` and resolve ambiguous/subdirectory roots. Select an existing cloud project or explicitly authorize creation with genuine source evidence. Journal generated identities before mutation; reconcile original pending IDs on resume. Additional projects do not reuse the wizard's first-project pointer. Memory requires no Git repository/configuration or explicit no-Git selection. Optional Git assistance separately confirms current branch, remote and accepted push URL; setup never publishes or changes branches.

Removal has independent project, local-machine and cloud selections. Present the complete target inventory, retained artifacts/costs and exact plan before approval. Preserve separate purge and abandonment decisions, barriers, private journals and pinned recovery code outside deletion roots. Status is observation; apply/resume can replay external effects. Never run self-removal entirely inside the MCP process being removed. Require the protected external continuation for actual stopped-harness/writer attestations. Preserve modified/shared/uncertain integration artifacts and report them as retained. Cancellation stops future work at safe boundaries, not already-submitted cloud effects; a snapshot is not proof of restoration or erasure.
