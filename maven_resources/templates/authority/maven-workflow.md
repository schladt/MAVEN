# Memory-first multi-session lifecycle and optional publication

Proposed skill: apply only as current applicable owner-approved cloud authority. Ordinary use is conversational through the shared memory controllers/MCP, not a CLI ritual. CLI/TUI remain deliberate recovery surfaces.

## Enable and initialize

Confirm the absolute root, selected instance and existing project or authorized creation with genuine source evidence. Reject `/`; do not auto-register the installation checkout or silently rebind an ambiguous/subdirectory root. Memory requires neither Git nor a no-Git selection. Journal generated identities before mutation and preserve interrupted setup receipts.

For explicitly enabled projects, native harness guidance initializes subsequent supported sessions. Show `MAVEN: initializing for <project>...`, then ready only after binding and complete current applicable authority/dependencies, handover, tasks and blockers load. Show paused readiness or a precise initialization-blocked reason as appropriate. A new project's absent handover is normal; missing authority is not. If automatic startup is unavailable, disclose the gap and initialize explicitly with visible chat output. Tool discovery, a server process or stderr logs are not readiness.

Retain explicit root/project/MAVEN session binding across cwd changes and restoration. Associate real harness-session metadata only when reliably exposed. New/forked sessions receive distinct identities; resume only the original explicitly selected session. Never use the newest receipt or another chat's identity. Reload current authority after compaction; tree navigation does not undo external writes or restore obsolete approvals.

## Checkpoint and closure

Ordinary checkpoints are nonblocking point-in-time operations where the harness supports later completion. Capture an explicit cutoff over accepted work and relevant source context; finish included assignments before declaring saved. New discussion/assignments belong to subsequent maintenance. Store a coherent truthful handover and exact immutable record/revision references. Later changes must not rewrite historical meaning. Pending, conflicted or uncertain included work leaves the checkpoint pending/blocked. Use an explicit checkpoint-and-wait request for synchronization through that boundary; foreground-only clients disclose their limitation.

Checkpoint waiting is bounded and may return pending honestly; it does not launch reasoning. Retain the original checkpoint identity, finish included assignments with the harness worker or foreground fallback, then advance that same boundary. Do not replace it merely because a wait expired. A worker on a separate MCP connection resumes the originating session with its assignment ID and actual originating harness binding; a worker sharing the main connection must not rebind it. Preserve returned worker tokens and use assigned change sets, not independent saves.

Wrap-up reconciles required memory work and closes only the selected session after verified persistence and no unresolved closure-blocking memory operations. Unpublished source can be reported as unfinished work without blocking closure. Memory checkpoint/closure never backs up files, commits, pushes, activates instructions, closes peers or revokes shared credentials. Show summaries at checkpoint completion, explicit wrap-up and on request, distinguishing universal promotions/updates, project updates and pending work. Keep routine maintenance successes quiet.

## Pause, resume and outage

Pause automatic maintenance only in this session. Stop new automatic assignments and pause active work at safe boundaries where available; already-submitted writes may complete. Preserve accepted assignments and receipts. Do not build a separate archive/backlog of paused discussion. Explicit save, consult and checkpoint remain available and instruction checks stay in force.

Default resume reviews available paused discussion and creates bounded catch-up work; disclose inaccessible portions and never claim complete reconstruction. Resume fresh does not look back. Persist mode and available context anchor without copying the whole transcript. Announce mode changes visibly.

During outages preserve bounded authorized work and exact operation receipts privately. Distinguish locally pending, cloud-saved, blocked and uncertain; never report explicit saves/checkpoints complete without verified cloud receipts. Unrelated work may continue, but current-memory/authority dependencies wait. Recover original request identities after rereading current records; never silently log in, switch accounts, clear locks or discard evidence. Read-only status is separate from recovery that can replay writes. Cancellation is not rollback.

## Optional Git safety

Only explicit Git intent selects publication. Confirm actual current branch, remote and accepted push URL separately from memory enablement. Preserve dirty work and unrelated commits; never pull, merge, rebase, reset or switch branches automatically. Register cooperating writers, obtain the publication reservation and truthful peer quiescence, then inspect the exact candidate. Run only project-configured checks. Do not infer file ownership from the session.

Show paths/digests, HEAD, destination, pre-existing commits, check results and proposed effects. Commit/push requires approval of that exact action-specific candidate; changed bytes/HEAD/destination require new review. A checkpoint or wrap-up request is not unseen-publication approval. Unknown outcomes require the original receipts and explicit reconciliation, not blind retry or destructive repair. Local coordination cannot stop arbitrary editors or other hosts.

Keep publication recovery separate from memory operations. Do not relabel a historical Git checkpoint or reinterpret a pending approval as a new memory checkpoint. Resolve incompatible old operations through their original supported implementation before cutover. Preserve exact writer-token evidence; age does not prove a writer died. Explicit logout/security cleanup has separately reported shared-access consequences, not proof of cloud closure or provider token revocation.
