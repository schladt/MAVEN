# Cloud memory and revision-safe records

Proposed skill: use only after explicit owner review/activation and retrieval as current applicable cloud authority. Select the private instance explicitly and validate the configured runtime identity; never fall back to another account or deployment role.

Use typed memory operations through MCP over the existing verified cloud client. Discover records then read exact current bodies and full instruction dependencies. Default search covers universal plus current-project records; explicitly select universal, another project or owner-wide consultation when intended. Use IDs, revisions, hashes and request keys from actual responses, not guesses. Ordinary reference knowledge never becomes authority merely by being stored or promoted.

## Semantic maintenance

Automatically maintain authorized meaningful decisions, tasks, plans, blockers, verified outcomes and handovers, and honor explicit save/consult/reconcile requests. Preserve source evidence and uncertainty. The maintenance role receives a bounded assignment with originating session, allowed scope, affected work, context, generation and operation identity. Where the harness supports responsive native background subagents, delegate actual retrieval, reasoning, reconciliation and submission; otherwise perform them in the foreground. MCP and deterministic network workers do not supply semantic reasoning.

Retrieve current records before deciding changes. Choose project or universal scope, preserving source record/revision and local caveats when promoting general knowledge. Routine scope classification/promotion needs no separate per-record approval. Support corrections without erasing history or activating instructions. Independent work may proceed safely; serialize conflicting work and reject superseded results. Expected revisions and task-claim fences complement assignment ordering. On a revision conflict reread and reconcile; escalate only material unresolved decisions.

Journal identity before submission. Keep per-effect verified progress and a completion manifest for multi-record changes; never claim atomic completion from partial success. Background workers must not overwrite a shared pending-request slot, start replacement sessions or lose original ownership. Surface pending assignments when answering from records that may still be changing.

## Receipts and outages

Explicit saves confirm only verified cloud results. Distinguish pending locally, cloud-saved, blocked and uncertain. During outages preserve bounded authorized assignments and original request receipts privately, report degraded state and continue unrelated work. Dependent work waits for current authority/memory; stale instructions are not fallback authority. On recovery fetch current records before semantic reconciliation and reconcile uncertain writes using original request keys, not blind duplicate writes. Status is read-only; explicit recovery may replay a mutation. Never discard evidence to unblock a queue.

## Governing instruction changes

Instruction changes require draft, exact challenge, full owner review and activation bound to the current candidate hash. Activate dependencies before dependents and reread active results. Never bulk-activate starter proposals, fabricate consent or cache revoked instructions. Service/schema upgrades and policy activation are separately reviewed actions; local implementation/template updates authorize neither. Recover incompatible historical operations through their original supported path before cutover.
