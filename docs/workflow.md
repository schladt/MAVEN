# Project and session workflow

## Normal work inside OMP

Install/connect the cloud instance once; the installer's project step can be deferred.
Open OMP in the project you actually want to work on, with the installed generic
skills discovered, and invoke:

```text
/skill:maven-start-work
```

The assistant confirms the absolute project root. It never automatically uses the
MAVEN installation checkout or filesystem `/`; ambiguous roots and subdirectories
require a choice, not a silent change to the Git top-level directory. The source
checkout can be a development project only after explicit selection.

On **first use**, the assistant offers project setup in chat: choose an existing
cloud project or authorize a named new one with real source evidence, and confirm
the detected remote/push URL/current branch or explicitly choose no-Git. Setup
generates and durably journals new project/request UUIDs. You need not invent UUIDs,
open another terminal, or assemble session commands. On a **configured project**,
the selection is preserved and validated; repeated setup does not create a project.
Additional projects use the same skill in their own selected folders, not another
instance deployment or the instance wizard's saved first-project pointer.

Start returns complete approved cloud instructions/dependencies, the prior completed
handover, tasks, blockers and peers. The assistant reads all of them and applicable
references before work, including all ranges of truncated output. A missing handover
is normal for a new project; missing authority or access blocks work. Cached
instruction bodies and OMP transcripts never replace cloud authority or persistent memory.

Each new harness session has its own MAVEN UUID, distinct from any optional OMP
session identity. The assistant retains this chat's root/project/MAVEN binding
across cwd changes. Repeating the start skill in this chat inspects and refreshes
that binding instead of starting another session. An actual harness-session ID is
included only when reliably exposed; omission is supported and never filled with a
guess. Resuming a prior session requires explicit selection, not the newest local
receipt or another chat's UUID. There is no global current-session file.

Use `/skill:maven-checkpoint` to preserve progress, and `/skill:maven-stop-work` to
close only this session. Both save truthful memory and coordinate writers. Asking
to checkpoint/stop does **not** approve an unseen Git candidate: the assistant shows
the exact action-specific candidate and obtains approval before commit/push. Existing
local commits are never silently included. No-Git projects get durable memory-only
closure. Peers may need to pause; one stop does not close their sessions or log out
credentials they still need, including peers in another project.

The following commands are a manual/API reference, not an extra outside-harness
ritual. Values represent real owner choices and returned identifiers.

## Manual project setup reference

For owner-operated interactive setup:

```sh
maven-project setup --root "$PROJECT_ROOT"
```

After an agent has obtained all choices in chat, either of these noninteractive
forms is available; either project choice supports either Git choice:

```sh
maven-project setup --root "$PROJECT_ROOT" --non-interactive \
  --create --name "$PROJECT_NAME" \
  --source-origin "$OWNER_SOURCE" --source-excerpt "$OWNER_REQUEST" --no-git

maven-project setup --root "$PROJECT_ROOT" --non-interactive \
  --project-id "$PROJECT_ID" \
  --remote "$REMOTE" --accepted-url "$REPOSITORY_URL" --branch "$BRANCH"

# Preserve and validate an already configured project:
maven-project setup --root "$PROJECT_ROOT" --non-interactive
maven-project show --root "$PROJECT_ROOT"
```

For an unconfigured root, missing explicit project or Git/no-Git choices fail before
a cloud write. Real source evidence is required for creation; new project/request
UUIDs are generated by setup and saved before mutation. Keep each root's private
ignored `.maven/runtime` setup receipts (`0700` directories, `0600` files). Repeating
an interrupted setup reconciles original IDs before explicitly resuming a mutation;
never discard an uncertain receipt or mint another project. Preserve/adopt exact
legacy instance-wizard pending/saved IDs rather than using that state as an
additional-project pointer. Existing conflicting selections fail rather than rebind.

For a project without Git, use `--no-git` instead of the three Git destination flags.
The accepted URL and selected remote must describe the owner's intended repository.
Destination URLs must not embed credentials, signed queries or fragments. HTTP(S)
userinfo and URL passwords are rejected; use an owner-managed SSH or credential
mechanism instead. Ordinary HTTPS, SSH usernames/SCP syntax, explicit local paths
and file URLs are supported.
The workflow uses the current branch; there is no hard-coded canonical `main` branch
or automatic branch switch. The low-level `maven-project init` interface supports
optional project checks with repeated `--check '["program", "argument"]'`; MAVEN's
own test suite is not an implicit check for every unrelated project.
Before first publication, the configured remote branch must already exist and match
local HEAD. Establish that destination through a separately approved Git operation;
the workflow does not create a missing remote branch or silently publish local history.

`maven-project init --root "$PROJECT_ROOT" --project-id "$PROJECT_ID"` with the
explicit Git destination flags (or `--no-git`) remains the low-level binding API.
Its creation form additionally requires `--create`, `--name`, `--source-origin`,
`--source-excerpt` and `--request-key`, with exact caller-managed UUIDs. Prefer
`setup` for first use so those new IDs are safely generated/journaled for you.
Existing project files are retained rather than silently rebound.

## Manual start or resume

```sh
maven-start-work --root "$PROJECT_ROOT" --harness omp --json
# Resume only a specific, previously selected session:
maven-start-work --root "$PROJECT_ROOT" --resume "$SESSION_ID"
```

Use the returned MAVEN UUID as `SESSION_ID`. Add `--harness-session "$HARNESS_SESSION"`
only if the current harness reliably exposes that actual identity; it is optional
and distinct, not something to fabricate for OMP. Choose the actual harness name.
Start loads project context, previous completed handover, tasks, blockers and peers.
No previous handover is normal for a fresh project. Missing access/authority is not
the same as empty memory. Read every full instruction/dependency and applicable
reference before work. Start never pulls, merges, rebases, resets or switches
branches, and external commits do not require invented MAVEN receipts.

Older completed sessions without a completion timestamp are ordered by their cloud
record timestamp, not by their randomly assigned session UUID.

Keep cloud session records current as work proceeds. Use `maven-workflow
refresh-context --help` and `maven-workflow session-summary --help` for explicit
context refresh and summary management; those operations target the selected session,
not a global current project.
Project-bound record writes use `maven-memory record put "$PRIVATE_RECORD_FILE"
--root "$PROJECT_ROOT" --session "$SESSION_ID"`; claims similarly require both
selectors and a matching session in the request. Use managed lifecycle commands for
project session/checkpoint records, not raw record writes. `maven-memory skill list`
reads the cloud catalog without a local cache; `skill fetch --slug "$SLUG" --root
"$PROJECT_ROOT" --session "$SESSION_ID"` uses the selected session's private cache.

## Inspect, quiesce and approve

The skill request itself is not approval to publish. Retain the same root/MAVEN
UUID throughout inspection and apply, and do not replace a pending approval with
a new summary or candidate. Inspect `status` and explicitly cancel or recover first.

Stop active writes before attesting `--writers-quiescent`. It means the relevant
cooperating writers are actually quiescent, not that every process or the whole cloud
instance has been stopped.

```sh
maven-checkpoint --root "$PROJECT_ROOT" --session "$SESSION_ID" --writers-quiescent
```

Inspection reserves the repository and returns the reservation and any peers that
must acknowledge a pause. Each affected peer stops its work and explicitly pauses:

```sh
maven-workflow pause --root "$PROJECT_ROOT" --session "$PEER_SESSION_ID" \
  --reservation "$RESERVATION_ID" --writers-quiescent
```

Then the requester repeats inspection with its truthful summary and exact durable
memory reference as required by the response:

```sh
maven-checkpoint --root "$PROJECT_ROOT" --session "$SESSION_ID" --writers-quiescent \
  --summary "$SUMMARY" --memory-ref "$RECORD_ID:$REVISION"
```

Review the complete returned candidate and `proposed.approval_code`, current branch,
base HEAD, destination, paths/digest, existing local commits, configured checks,
memory references and proposed effects. Only after explicit approval of that exact
action-specific candidate, apply its returned code without rewriting memory:

```sh
maven-checkpoint --root "$PROJECT_ROOT" --session "$SESSION_ID" \
  --writers-quiescent --apply "$APPROVAL_CODE"
```

Do not combine `--apply` with `--summary` or `--memory-ref`.
Changing bytes, HEAD, memory reference or destination invalidates approval and requires
reinspection. Do not silently publish pre-existing local commits. If the workflow
blocks on them, reconcile their disposition with the owner rather than resetting,
rebasing or force-pushing.

A checkpoint keeps the requester active. To close only the requesting session, use
`maven-stop-work` in **both** inspection and apply. Checkpoint and stop approval codes
are not interchangeable. No-Git/unchanged candidates may finish durable memory
closure during inspection, without a Git approval candidate. Read `git_outcome`;
`not_applicable` or `unchanged` is not a commit or push. Confirm `checkpointed` or
`closed` and actual cloud/Git receipts; `ready` or exit 0 alone is not publication.
Exit 3/`approval_required` needs review, exit 2/`blocked` stops affected work, exit
5/`unsynchronized` can mean an external effect already occurred, and exit 4 is error.
Report cloud closure and failed cleanup separately rather than inventing success.

## Shared checkout and recovery

All cooperating write paths must use the session registry. New writers are rejected
while a repository reservation is active. Per-session receipts prevent one session
from overwriting another's state; they do not attribute shared files to particular
sessions. Peer HEAD advancement is reconciled without discarding session memory.

There is no automatic stale-lock takeover. Inspect `maven-workflow cancel --help`,
`resume --help` and `recover --help`, and the blocked command's report before choosing
an explicit recovery action. Preserve unknown-outcome receipts and exact request keys.
`maven-workflow status --root "$PROJECT_ROOT" --session "$SESSION_ID"` exposes current
reservation and writer tokens. Recovery of crashed writers requires the exact complete
token set with repeated `--writer-token TOKEN` and truthful `--writers-quiescent`.
Every `recover` invocation requires `--writers-quiescent`, even without `--apply`,
because exact cloud reconciliation can replay a pending mutation. `status` is the
read-only local inspection command. A peer's pending journal must be recovered before
it can acknowledge quiescence.
`cancel --approval-only` releases an approval reservation while retaining the session;
it is not a claim that a previously attempted external operation failed.
Do not clear locks, delete runtime directories, reset Git or retry publication blindly.
Cancel/release and peer resume are explicit steps, not proof that an attempted external
mutation failed. An unregistered editor or a different host can still race the workflow;
revalidation is necessary but cannot make arbitrary concurrent edits safe.

Closing an invocation releases its client. Stopping one project session must not log
out credentials still shared by active peers, including peers in another project.
Last-session cleanup can log out shared local access. Explicit
`maven-workflow logout --root "$PROJECT_ROOT" --session "$SESSION_ID"` removes the
selected shared local login/cache access and reports affected peer sessions, marking
them paused/access-revoked locally. It neither closes their cloud memory sessions nor
claims provider-side token revocation. Resume only after the owner's explicit fresh
login; no automatic renewal occurs. Authentication, identity, and validated-response
integrity failures also request shared-access cleanup and report affected sessions.
Transient transport failures preserve session state and receipts for explicit recovery.

## Detach or retire instead of stopping work

Stopping a session is not uninstalling MAVEN. Use the separately reviewed
[`maven-uninstall` workflow](getting-started.md#uninstall-and-retirement) to detach
a project, remove selected local installations, or retire/purge an instance.
These scopes never imply one another.

Project detachment retains cloud history by default. Explicit archival blocks new
project work without hiding history; reactivation is separately planned. Uninstall
barriers reject new local registrations and writer entry while leaving status and
recovery readable. Offline detachment preserves exact unresolved local evidence and
does not claim remote closure. Do not silently start another session to bypass a
removal or retirement barrier.
